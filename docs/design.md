# 设计与思路

## 1. 问题

报告 PDF 由 Chromium 打印生成。页面里的示意图是 SVG，而 SVG 用的是 `<pattern>` 填充：

```svg
<pattern id="cement_1" patternUnits="userSpaceOnUse" width="10" height="5.8">
  <line ... /><line ... /><line ... />
</pattern>
<path d="M92.5,496.9 L92.5,1158.6 ..." fill="url(#cement_1)" />
```

浏览器**不保留 pattern 语义**：它把整个填充区当着色器渲染成一张位图，
再以 `PatternType 1` + `Image XObject` 的形式写进 PDF。一个 38×23 的纹理单元
变成了 827×752 px 的图，一份 4.68 MB 的报告里 98% 是这种图。

后果有两个：文件巨大；放大后是马赛克（原始矢量已在导出时丢失）。

## 2. 走过三条路

### 路线 A：从 PDF 反推矢量（失败，耗时最久）

思路：既然图案是周期性的，就从位图里测出角度/间距，再用 PDF 的线段重画。

失败原因分三层：

1. **坐标系反推不可靠**。旧内容流开头有一个顶层 `cm`（`.24 0 0 -.24 0 841.92`）并且不被 `Q` 抵消；
   每张图还画在各自的 Form XObject 里、带自己的 `cm`；SVG 的 `viewBox` 不等于绘图包围盒；
   生成器还对绘图做了**非均匀拉伸**（横向 0.506、纵向 0.432）。任何一处估错 5%，
   摊到 700 pt 的列上就是 35 pt 的错位。
2. **pattern 语义不同**。浏览器画 pattern 内容时**不裁到 tile**，PDF 的 tiling pattern
   **会裁到 BBox**。一个 10×5.8 的 tile 里塞 3 条跨度 26 的线，PDF 只能保留碎片，
   密度凭空少 2/3。
3. **验证成本高**。环境里没有可用的 headless 浏览器，每个假设都要"渲染 + 像素比对"，
   而"看起来对"往往掩盖几 pt 的系统性偏移。

结论：**信息已经丢了，反推只能得到"像"，得不到"是"**。

### 路线 B：小位图平铺（有效但不是终点）

既然图案是周期性的，就只存一个周期，让阅读器去平铺。

- 效果：4.68 MB → 130 KB，纹理细节在 600 dpi 下与原图逐像素一致；
- 但它是**从 72 dpi 位图里裁的周期**，放大后仍然是马赛克，只是马赛克变小了。

作为"拿不到 SVG"时的备选，它是合格的；但它解决不了"清晰"。

### 路线 C：从 SVG 直接发射矢量（采用）

对照一份"效果很好"的参考 PDF（467 KB，其中 410 KB 是字体，绘图只占约 20 KB）后确认：
**只要把 pattern 当成 PDF tiling pattern 正确发射，纹理和斜线都可以是矢量的**。

于是把任务重新定义为：

> 输入报告 + 生成报告时用的 SVG；输出报告，其中那一列由 SVG 重新发射为矢量。

坐标不再反推，而是由生成端提供**绘图框**（`--rect`，PDF 点）。所有几何只有一个仿射。

## 3. 现在的管线

```
apply(report.pdf, drawing.svg, --rect, --cover)
  ├─ 读旧内容流（原样保留）
  ├─ 解析 SVG：图元（transform 栈 + 属性继承）+ <pattern> 单元
  ├─ 建立仿射：viewBox → rect（sx, sy, tx, ty），y 翻转
  ├─ 发射：
  │    ├─ 斜线填充 → 大 tile + 整族线（见 pdf-pattern-notes.md）
  │    ├─ 点状纹理 → 单元 tile
  │    ├─ 普通路径 → rg / RG + m/l/c
  │    └─ 标注 → BT/Tf/Tm/Tj/ET
  └─ 合成：q 旧内容 Q → 白底(cover) → q 新内容 Q
```

`print` 是同一条发射器，只是 `place()` 退化成恒等变换——用来单独验证发射器；
**`print` 对了，`apply` 的错就只可能出在仿射上**。这个"分层验证"是后期效率提升的关键。

## 4. 关键数字（第二份报告）

| | 原件 | 输出 |
|---|---:|---:|
| 文件 | 4,787,503 B | 92.7 KB |
| 位图 | 52 | 0 |
| tiling pattern | 0（全是位图 pattern） | 5 |
| 文字 | 2,558 字符 | 2,772 字符 |

600 dpi 下：套管壁斜线墨量 0.250 / 0.233 与原件完全一致；点状纹理 mean / std 逐项相同。

## 5. 教训

1. **不要在没有信息的地方做推断**。能从生成端拿到 box，就不要从像素里估。
2. **同一份文件里可能有多个坐标系**（页面默认空间、Form 的 CTM、pattern 空间、SVG 用户空间），
   每个 pattern 的"单位 → 页面"比例都可能不同。
3. **分层验证**：能用 1:1 的独立页验证的，就不要在复杂页面上验证。
4. **两套渲染模型的语义差异要当成硬约束**（tile 裁不裁），而不是当成 bug 去试。
